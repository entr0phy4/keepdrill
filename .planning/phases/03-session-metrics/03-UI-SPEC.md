# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope of this phase's UI (per 03-CONTEXT.md + 03-RESEARCH.md):** a new results panel that
> appears automatically the instant an exercise completes (D-05), showing net WPM (METR-01),
> accuracy (METR-02), and the five slowest keystrokes or a "not enough data" fallback (METR-03).
> The existing trainer surface (caret, per-character coloring, whitespace glyphs — Phase 2) and
> the existing Restart control (Phase 2) are **not modified in appearance**, only extended: the
> Restart control remains reachable from the results view (D-06), and `CaptureSurface` gains one
> new `onComplete` callback prop (D-07) with no visual change of its own. This phase does **not**
> add persistence, a per-digraph/heatmap view, or any historical/progress display (all ANLY-*/
> PERS-*, explicitly v2).
>
> **This EXTENDS `01-UI-SPEC.md` and `02-UI-SPEC.md`.** All spacing/typography/color tokens below
> are inherited unchanged unless explicitly introduced as new. Do not re-derive the token
> foundation.

## Spacing Scale

Inherited unchanged from `01-UI-SPEC.md` (multiples of 4 only): `--space-xs` 4px, `--space-sm` 8px, `--space-md` 16px, `--space-lg` 24px, `--space-xl` 32px, `--space-2xl` 48px, `--space-3xl` 64px. No new spacing tokens needed.

**Layout for this phase (new — the results panel):**

- **Placement:** the results panel renders **below** the trainer surface (`CaptureSurface`) and **above** the existing Restart button — DOM/visual order becomes: trainer surface → results panel → Restart button. This is a pure insertion; the trainer surface and Restart button do not move or change.
- Gap between the trainer surface and the results panel: `--space-md` (16px) — matches the existing gap already used between the trainer surface and Restart in `App.tsx`'s layout grid.
- Gap between the results panel and the Restart button: `--space-md` (16px) — same token, no new value.
- **Panel container:** a bordered Secondary-surface card, `--space-lg` (24px) internal padding, `border-radius: 6px`, `border: 1px solid var(--color-border)` — the same visual treatment already used for `.preview` and `.banner` (Phase 1), reused rather than re-invented.
- **Internal panel layout:**
  - Panel heading ("Results") → `--space-lg` (24px) gap → stat row (WPM + accuracy) → `--space-lg` (24px) gap → slowest-keys section.
  - Stat row: a 2-column CSS grid at `≥ 640px` (matching Phase 1's existing `@media (min-width: 640px)` breakpoint), collapsing to a single stacked column below that, `--space-lg` (24px) column-gap / `--space-md` (16px) row-gap when stacked.
  - Each stat block: value → `--space-xs` (4px) gap → label caption below it.
  - Slowest-keys list: `--space-xs` (4px) gap between list items (a tight, compact list — these are short one-line rows, not cards).
  - Each list item internally: key-chip → `--space-sm` (8px) gap → latency value.

**Exceptions** (rendering primitives, not layout spacing — same category as Phase 1/2's 1px borders / 44px hit-target floor / 2px caret rule):
- Key-chip padding: `--space-xs` (4px) vertical, `--space-sm` (8px) horizontal — this is the chip's own internal padding, not a layout gap, sized to read like a compact `<kbd>` badge rather than a full control.
- Key-chip border: 1px, `--color-border` (same weight as existing buttons/textarea borders).

No independent scroll container on the results panel — it is always short (3 stats + at most 5 list rows), unlike Phase 1's `.preview`; nothing about this phase's content can grow unbounded.

## Typography

Inherited unchanged from `01-UI-SPEC.md` — reused, not redeclared:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 15px | 400 | 1.5 |
| Label | 13px | 600 | 1.4 |
| Heading | 20px | 600 | 1.3 |
| Display | 28px | 600 | 1.2 |

- **Panel heading ("Results"):** Heading role (20px/600/1.3) — same usage as Phase 1's "Exercise"/"Type here" region headings.
- **Stat values (WPM number, accuracy percentage):** Display role (28px/600/1.2) — the largest existing size, reused for visual weight through *size*, not through a new color (see Color section's rationale below — this deliberately mirrors Phase 2's own "correct text is not accent" reasoning).
- **Stat labels ("wpm", "accuracy") and the slowest-keys section label ("Slowest keys"):** Label role (13px/600/1.4), muted text color — same role Phase 1 uses for field labels.
- **Slowest-key latency values ("842 ms") and the key-chip glyph itself:** Body role (15px/400/1.5) — plain text weight, not emphasized; the chip's border/surface treatment (Color section) provides the visual distinction, not a heavier weight.
- **"Not enough data" fallback message:** Body role (15px/400/1.5), muted text color.

No italic, no letter-spacing adjustment, no new sizes or weights introduced — same 2-weight discipline (400/600) as Phase 1/2.

## Color

Theme continues to follow `prefers-color-scheme`, no manual toggle. **Phase 3 introduces zero new color tokens and zero new accent usage** — every color used in the results panel is one of the existing tokens from `01-UI-SPEC.md`/`02-UI-SPEC.md`.

| Role | Token | Usage in this phase |
|------|-------|----------------------|
| Dominant (60%) | `--color-bg` | Page background — unchanged |
| Secondary (30%) | `--color-surface` | Results panel card background; key-chip background |
| — border | `--color-border` | Results panel card border; key-chip border |
| — text primary | `--color-text` | Stat values (WPM, accuracy), slowest-key latency values, key-chip glyph text |
| — text muted | `--color-text-muted` | Stat labels ("wpm", "accuracy"), "Slowest keys" section label, "not enough data" message |
| Accent (10%) | `--color-accent` | **Not used anywhere in this phase's new UI.** |

### Why the stat numbers are NOT accent-colored

A typing-test result screen commonly highlights its headline number in a bright/accent color. **Rejected here deliberately**, for the same reason Phase 2 rejected accent-green for correct characters: Phase 1/2's accent reserved-for list is explicit and exhaustive by design (60/30/10 discipline), and this phase's own `03-CONTEXT.md`/REQUIREMENTS.md explicitly rule out gamification framing (`REQUIREMENTS.md` Out of Scope: "Gamification... optimizes for engagement, not skill"). Coloring WPM/accuracy by a good/bad threshold, or even just accent-highlighting them for emphasis, would be a step toward a scoreboard aesthetic this project has already ruled out. Size (Display role, 28px/600) carries the visual weight instead — exactly the same resolution Phase 2 already used for "correct" text.

**No performance-threshold color-coding**: the WPM and accuracy values render in the same `--color-text` regardless of their numeric value — there is no "good" green / "bad" red banding on these numbers. This is an explicit, locked rule, not an oversight.

### Accent reserved for (unchanged from Phase 2 — no additions)

1. Primary buttons ("Load exercise", "Restart exercise") — unchanged.
2. The focus ring on every interactive element — unchanged.
3. The capture `<textarea>`'s border while focused — unchanged.
4. The custom trainer caret — unchanged.

Phase 3 adds no fifth entry. Accent stays exactly as scarce as Phase 2 left it.

## UI Considerations

> Shape-rooted UI *state* coverage. Empty-state and error-state COPY live in `## Copywriting
> Contract` above; this section covers STATE coverage. Probe surfaces for this phase: E1 results
> panel container (auto-reveal), E2 WPM stat, E3 accuracy stat, E4 slowest-keys list, E5 "not
> enough data" fallback, E6 the existing Restart control (Phase 2, reconfirmed only — not
> re-probed as new). Resolved: **9 explicit, 3 backstop, 0 unresolved.** The planner MUST lift
> each row below into a plan's `must_haves`.

### Resolved — explicit (lift as `must_haves.truths` strings)

- The moment `TrainerState.completedAt` transitions from `null` to non-null (surfaced via `CaptureSurface`'s new `onComplete` callback, D-07), the results panel (E1) renders automatically, in the same render pass — no button, no separate "view results" action, no additional delay beyond the current frame (D-05).
- The results panel (E1) always renders all three metric groups together and in this fixed order: WPM (E2), then accuracy (E3), then the slowest-keys section (E4/E5) — matching METR-01 → METR-02 → METR-03's own ordering; none of the three is ever shown independently of the others.
- The trainer surface (`CaptureSurface`) remains mounted and visually unchanged in its completed state (per-character coloring, any still-incorrect positions, the caret) both above and after the results panel appears — Phase 3 adds a new panel below it; it never hides, dims, or replaces the trainer surface (extends Phase 2's own "complete ≠ all correct" rule to this phase's UI).
- The existing single Restart button (E6, unchanged from Phase 2) renders after the results panel in DOM order once results are visible; its click / Enter-Space-when-focused / Escape-while-capture-surface-focused behaviors are all unchanged (D-06) — no new confirmation step is added because results are now showing.
- Clicking Restart from the results view discards the just-computed metrics and unmounts the results panel, returning to the pre-typing trainer state exactly as Phase 2's `handleRestart` already does — mirrors Phase 2's own "no stale DOM/IME state survives" rule, now additionally covering "no stale metrics survive."
- When 1–4 characters clear the ≥3-post-filter-sample threshold (D-04), the slowest-keys list (E4) renders exactly that many rows (never padded to 5 with empty/placeholder rows) and carries no extra caption explaining the shorter count (silent partial rendering, per the Copywriting Contract's "Not introduced" note).
- When zero characters clear the threshold, the slowest-keys section is replaced entirely by the "not enough data" fallback message (E5) in place of the list; the WPM (E2) and accuracy (E3) stats still render normally above it — a partial metrics result (2 of 3 groups populated) is a valid, expected shape, never treated as a whole-panel error.
- A slowest-key entry whose logical character (D-03) is a space or a newline renders its key-chip using the exact glyph convention Phase 2 established for whitespace (`·` U+00B7 for space, `↵` U+21B5 for newline) — never a blank, invisible, or literal-whitespace chip — so a slow space/newline remains visually identifiable.
- The results panel container carries `role="status" aria-live="polite"`, so its appearance and the stat values it contains are announced to assistive technology the instant it renders — no separate visually-hidden summary string is needed since the visible text itself is the announcement content.

### Resolved — backstop (lift as `must_haves` flat scalars `{ statement, verification: backstop }`)

- statement: If `computeActiveElapsedMs` ever returns `0` at completion, the WPM stat (E2) renders "0 wpm" — never "Infinity wpm" or "NaN wpm" (RESEARCH.md Pitfall 2's engine-level guard, surfaced correctly at the display layer). — verification: backstop
- statement: The results panel (E1) appears with the same ≤150ms fade-in already used for Phase 1's banner-appearance transitions, wrapped in `@media (prefers-reduced-motion: no-preference)`, and causes no layout shift to the trainer surface or any content above it — it only expands the page downward, exactly as Phase 1's "loading an exercise expands the region downward only" rule. — verification: backstop
- statement: A slowest-key chip's rendered glyph never wraps, truncates, or overflows its chip — since D-03 groups by a single logical code point and the display substitution is at most the two-character whitespace glyphs above, the chip's content is always bounded to 1–2 visible characters. — verification: backstop

### Not applicable

- `loading` — metrics computation is a synchronous pure-function evaluation over an in-memory `charLog` (no async/fetch, per METR-04's "no I/O"); no spinner/skeleton state exists, mirroring Phase 1/2's own reasoning for synchronous operations.
- `zero-one-many` beyond the empty/partial rows above — there is exactly one results panel per completed session; the panel-level cardinality never varies (only the slowest-keys list within it does, already covered).
- `overflow` beyond the backstop above — the panel's content is bounded by construction (exactly 2 stat values + at most 5 list rows), unlike Phase 1's unbounded corpus preview; nothing in this phase's UI can grow past its container.

## Interaction Contract

**Everything below is additive to `01-UI-SPEC.md`/`02-UI-SPEC.md`'s Interaction Contract (theme, focus-ring, motion cap, no-layout-shift, caret rendering) — those rules are unchanged and still apply.**

- **Auto-reveal mechanism:** the results panel mounts on the `onComplete` callback (Pattern 3, D-07) — a `useEffect` in `CaptureSurface` keyed on its internally-computed `completedAt` transitioning from `null` to non-null, fired exactly once per completion. `App.tsx`'s existing 250ms `SESSION_REFRESH_MS` polling interval is explicitly **not** the trigger for this (RESEARCH.md Pitfall 6) — using it would introduce a visible, inconsistent lag between the completing keystroke and the panel appearing, contradicting D-05's "instant" requirement.
- **Focus:** no focus is moved programmatically when the results panel appears. Focus remains wherever it already was — typically still the capture `<textarea>`, since the panel appears as a direct consequence of the user's last keystroke landing. This keeps the existing Escape-to-restart shortcut (Phase 2) immediately usable without an extra Tab, and avoids yanking focus away from what the user was just interacting with.
- **No new keyboard exceptions:** this phase adds no new `preventDefault` carve-outs and no new keydown handling — the results panel is pure output, not an input surface. Restart's existing Escape shortcut and click/Enter/Space handling (Phase 2) are unchanged.
- **Motion:** the results panel's fade-in (see UI Considerations backstop) is the only new motion this phase introduces; it uses the existing 150ms motion cap already established in `01-UI-SPEC.md` and is wrapped in the same `@media (prefers-reduced-motion: no-preference)` block. No per-character animation, no counting-up number animation, no confetti or celebratory motion of any kind — the numbers appear at their final rounded value immediately, consistent with the "no gamification" rule above.
- **No layout shift:** the results panel only ever appends below the trainer surface and above the Restart button, expanding the page downward — it never reflows the trainer surface, the banners, or anything above them (same rule as Phase 1's preview region and Phase 2's whole layout).
- **Rounding discipline (executor note):** the metrics engine itself must return raw, unrounded numbers (RESEARCH.md Pitfall 5) — `Math.round()` (or equivalent) is applied only in the UI layer, at the moment of formatting a stat value or a slowest-key latency for display, never inside the pure `metrics.ts` module and never before sorting/ranking the slowest-5 list.
